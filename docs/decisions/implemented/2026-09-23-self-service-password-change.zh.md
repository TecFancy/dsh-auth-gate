# D22. 设置面板自助改密：POST /auth/password，写盘成功后全踢会话

## 决定了什么

已登录用户在 dsh 设置面板里自助修改自己的口令，服务端只新增一条精确路由：

- **`POST /auth/password`**（仅 password 模式注册；token 模式不注册，未注册的
  `/auth/*` 仍走 prefix `/auth` 兜底 404）。请求体为
  `application/x-www-form-urlencoded`，字段 `current`（当前口令）、`password`（新口令）、
  `code`（TOTP 验证码，`totpMode !== "off"` 且该用户有 secret 时必填）。
  「两次新口令一致」只在客户端与 CLI 校验，不进请求体。
- **处理顺序冻结**：method 405 → `parseFormBody`（415/413）→ cookie 定位 `subject`（401，
  只认 cookie，不认 Bearer，与 `/auth/status` 一致；会话存储不可用 `sessions()` 为 undefined
  时同样是 401 `unauthorized`，因为 AuthService 未就绪时插件的 gate 已 fail-closed，不能再把
  「插件半启动」误报成运维故障 503）→ 独立限速桶 check（429）→ 读 `users.yaml` 快照（503，
  读失败不计失败；**这是锁外的判定读**，锁内的权威快照由 `mutateUsersFile` 的 mutator 收到，
  见下条）→ 恒时验证旧口令（**未知用户**跑 `DUMMY_HASH` 以保持存在性等时；**已知用户（含已
  禁用）**跑其真实哈希，通过与否再叠加 `disabled` 判定，与登录路径 P9 一致；失败
  `recordFailure` + 401 `invalid_credentials`）→ TOTP 校验（缺码/错码/同窗重放/`required`
  模式下无 secret
  **一律 `recordFailure` + 401 `invalid_totp`**）→ 策略校验（400 `policy` +
  逐条 `rules`，失败也计失败）→ `hashPassword`（抛错也走 503，与写盘失败同款，不计为口令错误）
  → 锁内 CAS + 写盘（503；写失败计失败但**绝不吊销会话**）→ **写盘成功后** `recordSuccess`
  → 吊销该 subject 的全部会话（**含当前会话**）→ 清 cookie → `200 {"ok":true}`
  （`content-type: application/json`）。
- **冲突窗口内宁可拒绝，也不覆盖写**：mutator 在 `mutateUsersFile` 的**锁内新鲜快照**上重新
  验证现口令（CAS 冲突后重跑 ≤3 次）。若他人并发改过同一用户的口令，锁内复核失败 ⇒ 503，
  绝不把新哈希盖到对方刚写的状态上。同理，`loadUsers` 注入的读**不是**锁内权威读，只是写盘前
  的存在/禁用/旧哈希判定。
- **顺序是硬约束**：先写盘成功、再吊销会话。反过来会出现「全被踢但密码没改」的可用性事故，
  且可被攻击者反复触发。
- **自助改密成功后清除 `must_change_password` 标记**（若存在）：该字段本期只在 schema 预留
  （见 D23），登录路径不读它；改密成功后在同一 mutator 里条件写回默认值（`false` 不落盘），
  避免将来 P2 的登录强制改密门上线时把刚改过密码的用户立刻再拦一次。
- **TOTP 二次确认共用登录路径的同一 `replayGuard` 单例**（`index.ts` 既有注入点，features
  之间不互引）：`verifyTotp` 命中后再 `replayCheck(subject, counter, code)`，任一失败一律
  401 `invalid_totp`。**同窗语义 = 等下一枚验证码**：刚登录用掉的 30 s 窗口再提交改密会被判
  重放，这是预期行为，UI 与文档都如此告知。**顺序取舍（有意为之）**：TOTP 校验排在策略与写盘
  **之前**，因此「策略不过」被拒同样会烧掉当前 30 s 窗口，用户必须等下一枚验证码再试；把 TOTP
  后置会扩大验证码的重放面（策略失败的重试不再受窗口约束），故本期不重排这个顺序。
- **独立限速桶**：`index.ts` 新建独立的 `LoginRateLimiter` 实例（与登录 limiter 不同实例、
  不同桶），桶键为 IP（`deps.clientIp?.(req)`）+ subject。成功时 `recordSuccess(ip, subject)`
  清桶，避免用户拿新口令立刻被自己刚触发的锁挡住；与登录分桶也避免「反复打改密端点锁死登录」
  的 DoS 放大。**写盘/哈希失败也计入该桶的失败**（保守选择，有意为之）：并发冲突导致一方
  503 同样 `recordFailure`，因此同一用户短时间内在多台设备上反复撞冲突，可能让改密端点短暂
  429。代价只落在改密本身：桶与登录桶完全独立，登录不受影响，所以不为此单独开豁免计数。
- **已知残留：会话撤销失败不重试**。写盘成功后调用 `revokeBySubject` 全踢；若**该步抛错**，
  实现选择「error 日志 + 仍返回 200」，既不重试也不降级成失败响应：
  `logger.error("sessions not revoked after password change: <subject> (<n> sessions)")`。
  理由：口令**已经变更并落盘**，报 503 会让用户以为没改成功，从而不重试（甚至反复重试），
  如实返回 200 才是对状态的诚实描述。代价如实记录、不美化：极端情况下会出现「新口令已生效
  但旧 cookie 仍可用」，这个窗口只能由会话 TTL（默认 7 天）兜底。实现上 `AuthService`
  已把「撤销该 subject 的会话」包成带 try/catch 的尽力回收辅助函数，失败只记 error 日志，
  异常语义不被吞进静默成功。**P2 候选：撤销失败重试/告警，本期明确不做。**
- **已知残留：同站子域 CSRF 向量未处理**。会话 cookie 固定 `SameSite=Lax`（`COOKIE_FLAGS`），
  跨站表单 POST 不携带 cookie，因此经典 CSRF 不成立；但当攻击者能控制本站的某个子域时，该向量
  依然存在。本期**不加 CSRF token**，也不改 cookie 属性，与上一条残留并列如实记录、不美化。
  P2 候选：双提交（double-submit）token。
- **客户端**：设置面板新增 `settings.section`（`id: "dsh-auth-gate-account"`，order 500），
  未登录不渲染表单；已登录显示四字段表单，`fetch` 提交并按冻结响应矩阵映射错误（401
  `invalid_credentials` / 401 `invalid_totp` / 400 `policy` / 429 `retryAfter` / 503）。
  成功文案明确告知「密码已改，请重新登录」，当前设备同样已被登出。
- **审计**：成功 `logger.info("password changed")`，失败沿用现有 `"login rejected"` 风格常量串；
  **任何日志不得含 current/password/code 明文**（有断言测试）。
- **冻结面修订**：路由模型由 M2 的「1 prefix + 3 exact」修订为**「1 prefix + 4 exact」**，
  第 4 条精确路由是 `/auth/password`。`docs/implemented/impl-m2.md` 的 M5/M15 行与正文按
  本项目惯例在本文件生效时一并注明「D22 修订」。

## 背景

在此之前，口令轮换只有离线通道（`dsh-auth user passwd`，见 D23）：部署在公网的管理员必须
登服务器、进 shell 才能改自己的口令。日常改密的阻力直接推高了「长期不换口令」的概率；
自助改密把这一步收回浏览器，同时不引入任何新的提权面。

技术上它是一个**已登录会话内的敏感操作**：请求里带着明文旧口令与新口令，动作是覆盖认证凭证
本身。因此需要同时处理四件事：会话定位（谁在改）、凭证核验（真的是本人）、二次确认（TOTP
用户不能只凭会话 cookie 改密）、以及改密之后**已有会话该怎么办**。前三点是从现有登录路径
自然延伸，第四点才是真正需要拍板的地方：改密的意义之一就是「把可能已经泄露的会话踢掉」，
所以不能只做「保存新哈希」。

约束来自既有冻结契约：M2 的路由模型（prefix 兜底 + 精确路由、同一 path 不能注册两次、无
method 路由靠 handler 内分发）、M3 的响应形状纪律（每类失败一个常量、不反射请求文本、
`cache-control: no-store`）、限速器的桶语义、以及 TOTP `TotpReplayGuard` 的 counter 粒度
「同 counter 二次提交即拒」。可行性评估（工作区
`notes/tech/dsh-auth-gate/password-change-feasibility-2026-09-23.md` §3）逐条复核过这些约束，
本记录把结论固化为决策。

## 考虑过的替代方案

- **单独的改密页（`GET /auth/password` + `302` + form 提交）** 否：会新增一条 GET 精确路由和
  一张新页面，撞 6 KB CSS 预算与反钓鱼身份块那一套；且 `302` 让 fetch 客户端把失败读成成功
  导航（D20 已论证过的同一个坑）。设置面板内 `fetch` + `200 {"ok":true}` 是与 `/auth/status`
  同源的既有点法：状态码就是结果，不需要重定向。
- **只踢其他设备，保留当前会话** 否：改密最常见的触发原因就是「怀疑凭证泄露」，此时**无法
  区分**哪个会话是攻击者的。保留当前会话等于把「我自己这台是干净的」当成前提，而这个前提
  恰恰无法验证；全踢（含当前）语义简单、可断言，用户重新登录一次的成本很低。
- **免 TOTP 确认（有会话 cookie 就够）** 否：会话 cookie 是长效凭证（默认 7 天），改密是
  凭证轮换；免确认等于「会话被偷 = 可永久接管账号（改密锁死真主人）」。要求验证码把这一步
  拉回「同时持有口令与设备」的强度，与登录路径一致。
- **登录路径强制改密分流（`must_change_password` 生效）** 否：本期只在 schema 预留
  `must_change_password` 字段（见 D23），登录路径**不读**它。强制分流要动登录成功路径、
  加一张强制改密页、处理「改密失败如何退出」等分支，工作量与回归面都不小；管理员重置口令
  本期走「重置 + 全踢目标会话 + 审计」（P2 管理面）。预留字段保证 P2 只加不返工。
- **与登录共用同一限速桶** 否：攻击者可以反复打改密端点把某个用户的桶打到 429，从而把该用户
  的**登录**也锁死（DoS 放大器）。独立实例、独立桶，互不牵连。
- **在改密端点里使用独立 `replayGuard` 实例** 否：同一枚 TOTP 验证码将在 30 s 窗口内被接受
  两次，等于把消费语义打穿。共用单例是 slice 边界（features 禁止互引）下唯一正确的形态，
  代价是「同窗需等下一枚」，如实记录而不是隐藏。
- **新增 `GET /auth/users` / `POST /auth/users/password` 管理面一起做** 否（本期）：那是 P2，
  会新增 HTTP 提权面与审计需求。角色授予只走 CLI（D23），P1 不新增管理员操作端点。

## 为什么这样选

这是「在设置面板里把口令轮换还给自己」的最小服务端改动：只加一条精确路由、一个 feature 文件
与一个 shared 策略模块，不动路由模型的形状（仍是 prefix 兜底 + 精确路由），不动任何既有失败
形状，不新增依赖，不新增提权面。所有安全判断都复用了已经在生产验证过的部件：恒时口令验证、
`DUMMY_HASH` 存在性等时、`LoginRateLimiter`、`TotpReplayGuard` 单例、`buildSetCookie` 清 cookie。

顺序硬约束（先写盘、再吊销）把最糟的失败模式（全被踢但密码没改）从实现里结构性排除，
写盘失败只回 503 并保留全部会话。反方向（写盘成功但撤销失败）无法在同一事务里消除，团队
明确选择「如实返回 200 + error 日志 + 不重试」，并把「旧 cookie 残留到 TTL 到期」记为已知
残留而非静默略过。全踢含当前会话让「改密 = 终点」语义可断言，也让 E2E 的判据简单：改密后
原 cookie 必须失效、必须重新登录。TOTP 共用单例带来的「同窗等下一枚」是明确写进文档与 UI
的已知行为，不是缺陷。
