# D27. 宿主走廊末尾改用下界：`engines.dsh` 与 storage-domain peer 同时声明 `>=0.2.0-rc.1`

## 决定了什么

声明的宿主走廊末尾由替代项改为下界——顶层 `engines.dsh` **与**
`@deepseek-ai/dsh-storage-domain` peer 同时变为
`^0.1.0-rc.6 || ^0.1.5-rc.2 || ^0.1.7-alpha.1 || >=0.2.0-rc.1`。前面三个 caret 替代项保留，
用来记录真正验证过的 0.1.x 宿主线；末尾的下界接住当前 `next` 线及其之后的**一切**版本。
守卫测试（`src/shared/host-corridor.test.ts`）的期望串、覆盖断言与「不覆盖」断言同步改写。
**不改源码**，也不动 dev/测试宿主 cohort。

## 背景

dsh `0.2.0-rc.2` 的兼容闸门（`dsh-app-boot` 的 `evaluatePluginCompatibility`）只评估
`@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 的 `peerDependencies`，判定用
`semver.satisfies(runtime, range, { includePrerelease: true })`；`dsh plugin add` 的安装前预检
调的是同一个函数（`dsh-plugin-manager` 的 `operations.ts`）。带上 `includePrerelease` 之后，
下界的意思就是「此后所有版本都放行」，包括未来的预发布版本：

| 受检宿主版本 | D26 的走廊 | 本决定的下界 |
| ------------ | ---------- | ------------ |
| `0.1.5-rc.2` | 覆盖       | 覆盖         |
| `0.1.7-rc.2` | 覆盖       | 覆盖         |
| `0.2.0-rc.2` | 覆盖       | 覆盖         |
| `0.2.5-rc.1` | 覆盖       | 覆盖         |
| `0.3.0-rc.1` | 不覆盖     | 覆盖         |
| `0.3.0`      | 不覆盖     | 覆盖         |
| `1.0.0`      | 不覆盖     | 覆盖         |

上一行到倒数第三行的差别就是改动的全部理由。闸门判「不兼容」的后果不是报错，而是把这个插件包
**静默跳过**：实例照常对外服务，只是登录门不在了。D26 已把这种失败形态记作 fail-open。而追加
替代项是人肉动作，人肉动作滞后于宿主发版，滞后窗口就是 fail-open 窗口。

改动前收集的证据（2026-10-07）：

- semver 矩阵用仓库自带的 `semver` 复算，闸门参数取自 `dsh-app-boot` 源码
  （`lib/index.js` 里 `semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })`），
  本机运行宿主为 `0.2.0-rc.2`；
- **把范围写宽不会让 pnpm 多装一份 storage-domain**。线上 `web` profile 的 lock 里，
  `dsh-deeptutor@0.1.9` 声明的 peer 是 `^0.1.0-rc.6`，在宿主 `0.2.0-rc.2` 上既不满足严格口径、
  也不满足 `includePrerelease` 口径（caret 会展开成 `<0.2.0-0`），但 pnpm 依旧把依赖图里那份
  `0.2.0-rc.2` 给了它，整个 lock 里没有第二个 `dsh-tools` 版本。peer 去重用的是依赖图里已有的那份，
  `auto-install-peers` 只补图里根本没有的包。D12 当初那份重复副本来自 `dependencies`，不是 peer；
- 在 `includePrerelease` 口径下，`^0.1.0-rc.6` 一条已经盖住 `0.1.5-rc.2` 与 `0.1.7-rc.2`。
  0.1.x 那三条本来就是同一条线的重复，保留它们只是为了在声明和徽标里留下验证记录。

## 考虑过的替代方案

- **维持 D26 的枚举，每条新宿主线追加一次**——闸门不会误放行，但 dsh 换线当天登录门会静默消失，
  守住它靠的是人记得改声明。
- **整条走廊只留 `>=0.1.0-rc.6`**——最短，也覆盖今天所有在跑的宿主，但丢掉「在哪些 0.1.x 宿主上
  验过」这层记录；保留枚举零成本，所以没必要丢。
- **写 `>` 而不是 `>=`**——下界版本本身被排除，宿主恰好跑在下界上时，声明会把自己的最低支持版本
  判成不兼容，等于自己摘掉登录门。
- **每个宿主版本追加一项**——不必要：caret 在闸门口径下已经覆盖整条线，连尚未发布的预发布版本
  也在内，真正会漏的只有换线那一刻。
- **等 dsh 出稳定版再改**——闸门已经在用户从 `next` 装的 rc 线上生效，等待期正是需要覆盖的窗口。
- **给下界加上界（例如 `<1.0.0-0`）**——把「以后都兼容」缩回某条大线之内，可破坏性变更落在哪条线
  无法预知，加上界只是把同一个问题挪到下一个线边界。

## 为什么这样选

两个失败方向不对称。声明偏窄时，宿主判插件不兼容，插件包被静默跳过，登录门消失，实例照常对外
服务。声明偏宽时，插件照常加载，真遇到破坏性变更会在启动或运行时报错，属于响亮失败。对一个
登录插件来说前者不可接受，所以走廊在下界这一侧留宽；枚举保留下来，让声明、徽标和文档仍能读出
验过哪些宿主。

代价如实记档：未来的宿主如果在插件用到的接缝（`webServer` 路由表、storage 域、客户端槽位）上
出现破坏性变更，闸门不会再替我们拦住，插件会照常加载。声明只能表达意图，真正的兜底是运行时
自检：宿主起来之后探一次未登录访问，确认请求被挡在登录页。

本决定附一条**发版约束**：走廊必须随一个新版本出海。宽下界只对带它的插件版本生效，在此之前
dsh 一旦换到 `0.3.x` 线，线上装的仍是旧声明，照样会被静默跳过。
