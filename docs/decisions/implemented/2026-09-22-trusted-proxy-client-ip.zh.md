# D19. 限速桶的客户端身份改走受信反代头（`clientIpHeader` + `trustedProxyCidrs`）

## 决定了什么

新增两个配置项、两个叶子模块，并把「客户端是谁」从「TCP peer」改成「可信的客户端地址」：

- `clientIpHeader: string`（默认 `""`）—— 请求头名。**空串 = 一个头都不读**，限速桶 key
  就是归一化后的 `socket.remoteAddress`，与历史行为逐字节一致。
- `trustedProxyCidrs: string[]`（默认 `["127.0.0.0/8", "::1/128"]`）—— 受信反代地址集合；
  **只有直连 peer ∈ 该集合时**才会采信上面那个头。
- 新增 `src/shared/client-ip.ts`（策略解析 + 请求级取值 + 告警去重）与
  `src/shared/ip-address.ts`（IP 字面量归一化 + CIDR 匹配）。取 IP 算法固定为：
  读头 → 按 `,` 拆分 → 逐段归一化 → **从右往左跳过受信跳、取第一个非受信 IP**；
  缺失、不可解析、超长（>256B）、或全是受信跳 → 回退 peer 并告警（每类只一条）。
- 密码路径与 TOTP 第二段共用同一个取值点（`handlePasswordLogin` 只算一次 `ip`），
  因此两条路径的桶一定同源。

这是对 **P10**（「IP 取 `req.socket.remoteAddress ?? ""`，不读 XFF」）的**显式例外**：
默认语义完全不变；只有运营者显式配置头名、且请求确实来自受信 peer，才采信转发头。
配置写错只会**变窄**，绝不放宽、也绝不 fail-open：

| 配置问题                      | 行为                                   |
| ----------------------------- | -------------------------------------- |
| 头名不是 HTTP token           | 不读任何头（= 历史行为）+ error 日志   |
| CIDR 全部非法 / 为空          | 只信回环 + error 日志                  |
| 部分 CIDR 非法                | 丢弃非法项、保留合法项 + error 日志    |
| `0.0.0.0/0`、`::/0`（前缀 0） | 拒绝（等于「信任所有人」）+ error 日志 |

## 背景

issue #74（0.13.0，Cloudflare Tunnel + 回环）报的是：限速器用 `req.socket.remoteAddress`
标识客户端，而同主机反代（Tunnel / Caddy / nginx / Docker host 网络）下**每个请求的 peer
都是回环地址**，于是全站塌缩成一个 `byIp` 桶：

- 任何人累计 5 次失败 → 所有人的登录与 TOTP 提交在这段时间里 429，**即使密码是对的、
  那台设备一次都没失败过**；
- `recordSuccess` 清的是同一个共享桶 ⇒ 任意一次合法登录都会把全站失败计数清空；
- 反过来，经同一反代进来的攻击者与合法用户无法区分，per-source 减速失去对象。

代码级证据（0.14.0）：客户端标识的唯一来源是 `src/features/password/password-login.ts`
的 `const ip = req.socket.remoteAddress ?? ""`；`LoginRateLimiter.check` 取
`max(ipLock, accountLock)`，所以 IP 桶一锁，**所有账号**都被拒。仓库文档一直把
「按反代出口 IP 聚合」写成已知限制（P10 + `docs/deployed/*` 的「不信任
`X-Forwarded-For`」），但在这个拓扑下它不是限制，而是**全站可用性缺陷**：
本仓库自己的参考拓扑（Caddy 与 dsh 同主机、dsh 绑回环）就命中它。

## 考虑过的替代方案

- **无条件信任指定的转发头（issue 原文的 `trustedProxyHeader`）** —— 请求方只要能直连
  dsh（插件自称服务任意拓扑，dsh 可以绑任意网卡），就能伪造自己的桶、定向锁死别人、
  或灌满 `byIp`（上限 10000、超限删最早插入，可驱逐他人状态）。与 D14 拒绝
  `X-Forwarded-*` 的理由同源，不能采纳。
- **只按账号分桶 / 改成 `(peer, username)` 组合键** —— 跨用户误伤消失，但没恢复
  「不同真实客户端不同预算」；密码喷洒从「全站 5 次」退化成「每账号 5 次」，
  而且会掩盖「头没配上」的信号。
- **默认读 `X-Forwarded-For`，或取最左值** —— 最左可被客户端预置；默认读头等于把所有
  现有部署的限速语义建立在可伪造输入上。
- **缺头即 503 / 拒绝登录** —— 配置笔误会变成全站登录不可用，且难以与网关故障区分。
- **只改文档（保持现状）** —— 把 DoS 继续当限制写进文档，等于接受「任何人 5 次错密码
  就能让全家登不上」。
- **顺带改锁定语义**（IP 桶只做速率、账号桶做锁定，或去掉锁到期清零）—— 那是另一件事，
  会掩盖本次要验证的信号，另开 issue。

## 为什么这样选

「信 peer，不信头」与 express `trust proxy`、nginx `real_ip`、Go 标准库 `Forwarded`
的模型一致：转发头只是**受信 peer 声明的客户端地址**，可信性来自 peer 而不是头本身。
在这个模型下，默认配置（不读头）对所有既有部署零变化，唯一的效果增量发生在运营者
显式声明拓扑之后；而「从右往左跳过受信跳」是 XFF 链唯一安全的方向（客户端只能预置
更左的值）。IPv4-mapped 与 IPv6 归一化保证同一客户端始终落在同一个桶，也让
`127.0.0.0/8` 天然覆盖 `::ffff:127.0.0.1`。

前提与残余风险写进文档、不藏在代码里：受信代理必须**覆盖写入**该头（把客户端带来的
同名头原样透传，等于把伪造权交给客户端）；NAT/CGNAT 共享出口下的误伤依然存在
（账号桶是最后防线），与业界一致。
