# M3 遗留评估项维持不实施

## 决定了什么

M4 中重新评估了 M3 留下的三个 TODO 项，结论全部是**维持不实施**（各留
`TODO(auth-m5):` 标记）：
（a）`revokeBySubject`（禁用用户即时吊销已发会话）；（b）登录 CSRF token；
（c）限速器与防重放状态持久化。

## 背景

M3 冻结了「禁用用户只拦新登录、已发会话在 TTL 内继续有效」「登录不加 CSRF token」等
决策（P15/P21），并注明 M4 再评估。M4 引入 TOTP 两段式后，需要确证新增的挑战路径
没有改变这些结论，并给出最终处置，避免每一项无限期悬置。

## 考虑过的替代方案

- **（a）在 gate 路径内现读用户文件检查禁用状态** — 每次请求都做文件 IO 才能即时吊销，
  与 gate「零文件 IO、零 KDF」的冻结语义冲突（P12）；缓存会引入一致性问题。维持现状：
  单门模型里「禁用只拦新登录」的影响边界清晰，README 已注明局限。
- **（b）为登录/挑战新增 CSRF token** — TOTP 没有改变 P21 的分析：单门模型无用户间
  隔离，登录 CSRF 的后果只是 subject 审计值可能被污染，无权限边界损失；挑战路径的
  CSRF 提交需要攻击者知道受害者的当前验证码，本身不可行。`SameSite=Lax` + 现代浏览器
  第三方 Set-Cookie 限制继续收窄风险面。
- **（c）把限速/防重放状态落盘** — 登录低频率场景下，重启清零的窗口影响可忽略
  （攻击者也要重启才能清零，重置成本对防御方同样适用）；持久化引入 IO/竞态复杂度。

## 为什么这样选

三项都在「做」与「不做」之间有明确的安全收益递减：实现成本不小、收益在单门模型下
边际递减，且都有文档化的现状与局限。TOTP 两段式没有改变任何一项的前提假设。
「评估后明确不做」本身就是 M3 契约要求的收尾动作——把悬置项变成冻结决定，
未来如需重启再评估即可。
