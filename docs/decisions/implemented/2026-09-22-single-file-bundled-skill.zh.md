# D18. 随包技能保持单文件 SKILL.md（不启用 references/）

## 决定了什么

`.agents/skills/dsh-auth-gate-config/`（随 npm 包分发的配置速查技能）保持单文件：正文全部在
`SKILL.md` 里，不使用 `references/` 子目录。两条测试把这个决定锁进 CI：技能目录不存在
`references/`；`Config` schema 里的每个配置项都出现在技能正文里（新增或改名配置项必须先落到
技能）。将来若正文长到真正的附录量级，或 dsh 技能加载器出现正文大小上限，再重新决策。

## 背景

2026-09-02 曾把故障表与验证技巧拆进 `references/{failures,verification}.md`，主文件 13.9KB →
6.5KB，并安装到工作区实际使用；该拆分从未合并，随后被双语重写与后续版本取代。评估时确认了
几条事实：技能是 user-invocable only（`disable-model-invocation: true`），技能目录只暴露
frontmatter 摘要，正文仅在人显式打开时注入；`dsh-skill`（0.1.5-rc.2）对正文没有大小上限；
`references/` 不是加载器特性，正文里的路径要模型自己再读一次；`installSkill` 是整目录
`fs.cp recursive`，拆分出来的文件会照常装上，所以问题不在工具链。

代价出现在实测里：工作区那份拆分副本到 2026-09-22 仍是 6.5KB 的旧内容（`publicHost` 出现 0 次，
仓库版 3 次），stub 里写的「10 行原文」对应的故障表已长到 13 行。包内、`$DSH_HOME/skills`、
工作区 `.dsh/skills` 三份副本靠人工同步，而 `.agents/` 没有任何 CI 守护。被拆走的故障表与验证
技巧正是这个技能 description 承诺的内容（登录故障、限速），拆出去等于要多读一个文件才拿到答案。

## 考虑过的替代方案

- **按原方案拆分（主文件 + references/）** —— 省的是显式打开那一次的约 2.2k tokens，换来 stub
  计数腐烂、二次读取与三份副本的同步面；实测漂移已经发生，且指向的正是技能的主载荷。
- **按语言拆成两份（zh/en 各一）** —— 技能面板不能按语言选择，正文必须自带双语；按语言拆会让
  每次调用都要读两份。
- **保留单文件但压缩正文** —— 删掉的会是最容易被查的部分（故障矩阵）；速查技能的契约就是
  「打开即得答案」。
- **只写约定、不加任何测试** —— 同一个拆分会被再次提出，而 schema 与技能正文的漂移依旧无人拦。

## 为什么这样选

技能是用户显式打开的低频速查工具：目录面的成本只有一行摘要，正文成本只在那一次调用，省不下来
多少，而「打开即得答案」是它的全部价值。单文件同时把同步面从三份文件降到一份，并与仓库「一个
解释只有一个归属地」的行文纪律一致。两条测试只锁形状与同步性，不锁行文，将来有真实理由时改这
条记录即可。
