# Agent Note: 共享出口地址的锁定升级封顶在两分钟

Status: implemented

[English](2026-11-26-shared-egress-lockout-ceiling.md) | 中文

## Problem

issue #82：D19 之后桶键是真实的客户端地址，所以同一个出口地址（办公室 NAT、移动 CGNAT、VPN
出口）后面的所有用户共用一个 `byIp` 桶。一台设备输错五次口令，整个地址被锁。这是按地址限速的
常规代价（真正保护口令的是按账号的桶），但 D39 把它放大了：退避现在真的会升级，`strikes` 跨锁
到期保留，只有 600s 静默才衰减。于是一个繁忙的共享地址不再看到「反复 30 秒锁」，而是可能被按在
900 秒。

不对称的地方才是要点。账号桶指向一个可以被惩罚的主体：失败属于猜那个口令的人。地址桶指向一个
网络，而共享地址上的失败通常属于某一个人，锁却落在他的同事身上。对地址升级并不能增加对攻击者的
威慑（他就坐在同一个桶里，停手即可），只延长了附带伤害。

## Decision

`LoginRateLimiter` 只给 `byIp` 桶封顶：`ipMaxDelaySeconds`（默认 120s）；账号桶仍用
`maxDelaySeconds`（默认 900s）。两者继续共用 `maxFailures`、`baseDelaySeconds` 与 `windowSeconds`，
所以封顶之前的序列不变：30 → 60 → 120，之后地址停在 120，而被盯上的账号继续走到 240 / 480 / 900。

其余行为都保持 D39 定下的样子：IP 桶仍然会产生连带锁定（它就是横扫刹车）、登录成功仍然只清账号
桶、失败预算花完之后一次突发仍然只能放一条探测，且 `ipMaxDelaySeconds` 会被夹到 `maxDelaySeconds`
以内，调用方无法把地址的天花板设置得比账号还松。

这个选项是内部的：`RateLimitOptions` 上的一个带默认值的字段，不是插件配置键。需要不同天花板的运维
只能改代码，这样取舍留在一处可评审，而不是变成一个没人测过的部署旋钮。

## Alternatives considered

- **只写文档、维持 900 秒连带锁定（issue #82 选项 1）** —— 最省事，否决理由是：共享地址上的升级
  换不来威慑，攻击者就在同一个桶里，多出来的分钟只落在旁观者身上。
- **IP 桶改成节流而不是锁定（选项 2）** —— 固定短窗口能把伤害压得更低，但同时削弱了唯一同时覆盖
  横扫与无账号路径（token、passkey）的刹车：两次五分钟变每分钟约十次；而延迟式变体还要新增响应
  路径并占住连接。
- **失败跨多个用户名才锁地址（选项 3）** —— 每个桶要存一组账号键（基数与内存），对没有用户名的
  token / passkey 毫无帮助，而且有心的扫号者可以故意触发它。
- **加配置开关直接关掉 IP 桶（选项 4）** —— 等于去掉无账号路径与跨账号横扫的唯一保护；误读它的
  运维会把门禁变成只按账号锁定。
- **地址干脆不升级（固定 `baseDelaySeconds`）** —— 代码更少，但反对理由与节流相同：单个客户端可以
  永远以每三十秒五次的速度打那个地址后面的所有账号。

## Consequences

- 共享地址的最坏连带锁定从 15 分钟降到 2 分钟。扫号者每个地址的预算随之下降——大约每两分钟五次，
  而不是每十五分钟五次——这是有意的取舍：有心的扫号者本来就会换地址，而单个目标仍由账号桶兜底。
- 现在有两个天花板要在调参时一起考虑：`baseDelaySeconds` 与 `maxFailures` 同时移动两条序列，两个
  封顶各管自己的桶。
- 配置面没有变化，部署不需要新增设置；
  [`docs/deployed/known-limitations`](../../../../docs/deployed/known-limitations_zh.md) 说明了共享出口
  部署应当预期什么。
