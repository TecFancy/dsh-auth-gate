# Agent Note: Passkey-only sign-in

Status: implemented
Legacy ID: D38

[English](2026-11-16-passkey-only-login.md) | 中文

## Problem

issue #133 请求「绑定通行密钥后可以显式关闭密码登录」。D35 当初明确把 passkey-only 排除在 v1
之外，理由是「锁定与恢复路径不成熟（丢失全部设备且无口令 = 永久锁死）」。这次要重新评估的正是
那条理由还成不成立。

评估下来，锁定风险本身没有消失，但**可以把它变成运维可理解、可执行的一步**：策略写在配置文件里，
恢复就是把它改回去。真正危险的形态是「在 Web 界面上点一下就能关掉口令登录」——那会让一次会话
劫持变成永久锁死，而且恢复路径依赖一个已经被关掉的入口。把开关放在配置文件里，等于要求操作者
先持有服务器访问权限，这与 issue 第 5 点「恢复动作应由持有服务器访问权限的操作者主动执行」一致。

同时确认了仓库的模型边界：`docs/history/specs/dsh-auth-plan_zh.md` §0 第 1 条决定「不做多用户/会话隔离，
门保护的是整个实例」，`role: "admin"` 不是权限边界（[不做隔离的笔记](../architecture/2026-11-15-no-user-isolation.zh.md) 把这条写进了文档）。在这个前提下，
「某个账号单独禁用口令」没有意义——其他账号仍能用口令进同一个实例，而门内本来就不隔离。

## Decision

`passkey` 配置项增加第三个取值 `"required"`：实例进入 passkey-only 状态，口令与「口令 + TOTP」
都不能建立新会话，只有通行密钥可以。这是**实例级**策略，不是账号级——没有 per-user 的
「关闭口令登录」字段，也没有开启它的 HTTP 端点或设置页开关；开关它等于改配置文件加重启。

配套三条硬约束：

1. **配置失效不恢复口令登录。** `passkey: "required"` 而 `publicHost`/RP ID/origin 不成立时，
   功能降级为不可用，但口令登录**保持关闭**，登录页渲染带固定原因码的诊断卡。这是 issue #133
   第 4 点的落点，也是本决策与既有 fail-closed 语义唯一冲突的地方：既有的 fail-closed 是
   「关掉 passkey 功能」，这里必须升级成「关掉整个登录入口」。
2. **删掉最后一把凭据被拒绝。** HTTP 端点返回 `400` + `reason: "last-credential"`，判定在
   `mutateUsersFile` 的锁内复核（锁外快照挡不住两个并发删除）。CLI 读不到插件配置，因此一律
   要求 `--force`，而不是去猜实例是不是 passkey-only。
3. **恢复只有一条路：改配置回 `"optional"` 并重启。** 不提供 CLI 恢复命令，也不提供 Web 开关。

## Alternatives considered

- **账号级 `password_login_disabled` 字段 + 开启端点 + 设置页开关**（外部评审建议的方案）——
  没选。它需要：`users.yaml` schema 变更、新端点、会话记录加 `authMethod`/`passkeyCredentialId`
  以证明「这把 key 最近真的用过」、设置页单向开关、以及一整套并发事务测试。而它解决的问题
  （「多账号里只让一个走 passkey-only」）在一个不做用户隔离的模型里并不成立：另一个账号照样能用
  口令进同一个实例。工作量约 7–9 人日，收益是一个看起来像权限、实际不是的开关。
- **只加 `passkey: "required"` 但不改配置失效语义**——没选。那样 WebAuthn 配置一坏，实例会
  悄悄退回口令登录，正好违反 issue 第 4 点，也让「已开启 passkey-only」这个承诺变成假的。
- **加 CLI 恢复命令 `dsh-auth user password-login enable`**——没选。它要读插件配置才能判断该不该
  拦，而 CLI 与插件配置之间没有通道；退一步让它无条件清标志，等于给了一个绕过策略的本地后门，
  且与「改配置」这条恢复路径重复。改配置本来就是一步操作。
- **在设置页给一个「关闭 passkey-only」的开关**——直接否掉。会话被劫后攻击者能一键恢复口令入口，
  等于把策略降级成偏好。
- **开启时强制要求两把凭据**——没选。issue 只要求一把；擅自提高门槛会让「先注册一把试试」变得
  不可行。文档强烈建议两把，协议上只强制一把。

## Why

策略的载体决定了它的安全属性。放在配置文件里，开关动作天然要求服务器访问权限，恢复路径与开启
路径是同一条，不存在「关掉之后再也进不去」的形态；放在 Web 界面或 users.yaml 里，就多出一条
「被劫会话能改策略」或「坏状态读不出来、连 CLI 都救不了」的失败模式。

实例级而非账号级，是因为这个仓库的威胁模型本来就是单门：过了门的人共享同一个 dsh 部署。给一个
不做隔离的模型加账号级登录策略，会制造出「每个账号有自己的安全边界」的错觉，而这正是
[不做隔离的笔记](../architecture/2026-11-15-no-user-isolation.zh.md) 反对的那类误导。

代价如实写进 `docs/deployed/known-limitations.md`：管理员重置口令在 passkey-only 下**不恢复访问**
（重置仍设 `must_change_password`，但那枚受限会话只能靠登录拿到）；已有会话在过期前继续有效；
口令哈希保留，继续用于凭据变更的再认证，只是不能建立会话。
